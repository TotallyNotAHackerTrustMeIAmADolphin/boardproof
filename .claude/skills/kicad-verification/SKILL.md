# Verification workflow

This project's core design principle is **geometry over vision**: correctness comes from structured DRC/ERC/collision queries, never from rendering an image and looking at it. Follow this when asked to check a design:

1. **`pcb_run_drc(pcb_path)` is one complete DRC run, not the acceptance gate** (real `kicad-cli pcb drc` — track width, annular ring, unconnected items, shorts, silk-over-pad, etc.; its output says `not_the_gate`) and `sch_run_erc(sch_path)` is the authoritative ERC. Use these to see what is wrong; "is this board ready" is answered only by `verify_board`. Don't substitute the narrower placement check below for either. `pcb_check_placement` is a faster, narrower placement-geometry-only check (pad clearance/courtyard/edge/hole-to-hole) — useful as a quick sanity check right after moving/placing footprints, before routing exists to check, but **never report a design as DRC-clean based on `pcb_check_placement` alone**. A placement-only checker once shipped under the name `pcb_run_drc`, and this rule exists because of it. For placement-specific questions ("did these two footprints overlap", "is there room for this part here") use `pcb_check_collisions`/`pcb_validate_proposed_placements` directly rather than eyeballing a render.
2. **Evidence-gated verdicts — this is the habit that matters most**: every one of these tools returns an explicit `status` field (`ok`/`incomplete`/`error`/etc., check the actual tool's return shape). If `status` is anything other than a clean pass, **say so plainly** — never report "looks good" or "DRC passed" when the underlying check was partial, errored, or couldn't run. A tool reporting `incomplete` is not the same as a clean result; don't round it up to sound more confident than the evidence supports.
3. When violations are found, prefer fixing the *class* of violation across the board in one pass over fixing one instance, re-running the check, fixing the next instance, etc. — this project's tools are meant to support batch fixes, not a fix-one/recheck/fix-one loop.
4. If a violation has no clean automatic fix after a reasonable number of attempts, that's exactly the kind of case docs/ARCHITECTURE.md's human-in-the-loop policy calls for a checkpoint on — surface it clearly rather than forcing an automated "fix" that might not actually be correct (e.g. moving a footprint to technically clear a clearance rule without checking it still makes electrical/mechanical sense).
5. **Read complete lists, never samples or counts.** A board is routed or done only on a `verify_board` PASS (docs/TESTING.md's acceptance gate): zero unconnected items on every net, zero error-level DRC, and all zones filled, all from `kicad-cli`. `verify_board` is always available (no `load_toolset`), and every board-state output carries `gate: {verdict, board_sha, project_sha, verdict_board_sha, age_s, stale, note}` for that exact file; a verdict is `stale` after any mutation, and no tool but the gate may say routed or done. Whatever the verdict, report the full per-net unconnected list and the full violation list. `pcb_run_drc` reports `violation_count: 0` on a completely unrouted board, and a sampled check once declared openMPPT done with 13 signal-net connections missing. Never take positions from `kicad_tools` convenience properties without checking the raw S-expression.
6. Rendered SVG/PDF export (`kicad_cli.export_svg`) is a secondary, human-facing aid only — fine to produce when a human wants to actually look at the board, never as the basis for an automated correctness claim.
