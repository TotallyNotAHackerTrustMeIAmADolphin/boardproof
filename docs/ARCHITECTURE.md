# Architecture

**This file is the decision record, not the current overview.** For a ten-minute picture of what the project is and how it works, read [docs/OVERVIEW.md](OVERVIEW.md) first; the glossary is [docs/CONTEXT.md](CONTEXT.md). Come back here for the reasoning behind a design choice and for the known facts and gotchas with their evidence. Entries are dated and some are historical: where a later decision replaced an earlier one, the entry says so. "Build ticket N", "ticket N" and "protocol N" are explained in docs/CONTEXT.md.

This file records the current design, the decisions behind it, and the known facts and gotchas with their evidence. It was rewritten for the 2026-10-11 pivot. The full history (sprint logs, investigation narratives, the September prior-art survey) was in git at commit `3380b34` (the backlog, the research notes, older versions of this file), which belongs to the maintainers' archive and may not exist in a public copy. Ticket IDs such as P4-07 refer to that commit's backlog; they are historical references.

## Product shape (pivot, 2026-10-11)

- **Tiered promise by board class** (terms are defined in docs/CONTEXT.md). The **Autonomous tier** covers board classes below a measured complexity ceiling. Above that ceiling is the **Copilot tier**: the human owns power routing and zone topology, and the agent assists with schematic, placement, signal routing and verification. Copilot is the default. A board class becomes autonomous only once it passes the acceptance gate.
- **Acceptance gate**: only a `verify_board` PASS may call a board routed or done. docs/TESTING.md defines it.
- **Acceptance ladder**: rung 1 is the USB-C ATtiny1616 breakout, rung 2 a mid-size signal-only 2-layer board (about 30 nets), rung 3 openMPPT. The first rung that fails marks the autonomous ceiling. docs/ROADMAP.md has the details.
- **Why**: the external evidence (PCBWorld benchmark, arXiv 2607.05915, summarised in the maintainers' research notes) shows clean autonomous routing only for signal-only 2-4 layer boards of up to about 40 nets / 100 pads. In that benchmark, "routed" and "clean" diverge: Freerouting reaches routability 1.00 but a Clean Pass rate of only 0.78. Every LLM agent scores 0.00 Clean Pass at 5-42 nets. openMPPT (68 multi-pad nets, 488 pads, 7 zones, a 20 A class) is outside the evidenced envelope. This project's own month on openMPPT ended without a clean route.

## Decision history (2026-10-11 and 2026-10-19)

The design changed twice by review: the paradigm review of the 2026-10-11 pivot, and a second review (`paradigm-review-2`, 2026-10-19; its tickets are cited by number) after a study of mixelpixx/KiCAD-MCP-Server (v2.8.2) and the first rung measurements. Each 2026-10-19 verdict was decided with the owner in a grilling. Fixed inputs, not reopened: the acceptance gate, the tiered promise, the acceptance ladder, the openMPPT freeze and the hard-rule-2 cross-check. The resulting design is stated once, under "Decisions"; this section keeps only the reasons and evidence that are not stated there. The build work is in the numbered build tickets (docs/CONTEXT.md).

**2026-10-11 (pivot)**
- **Batch tools over one-item-per-call: kept.** The best LLM mode in PCBWorld (interactive with DRC feedback) is a loop of batch calls.
- **Two operating modes, live IPC and headless file: partly unsupported.** Only the 9 `copilot` tools go through `resolve_backend()`; the other 10 toolsets are file-only; live schematic reads are broken in kipy 0.8.0. Copilot became a **tier** (a promise), separate from the **adapter mode** (IPC vs file); the Copilot tier does not need live IPC, so file-drift detection (designed, never built, P1-19) is a prerequisite for it (decision 12).
- **`kicad-tools`: kept for file I/O and courtyard geometry, demoted elsewhere.** It is MIT and covers schematic, PCB and footprint generation, so there is no viable non-GPL alternative, and it has produced more than 15 silent bugs here (see "Known facts and gotchas"). It is never a verification authority (`kicad-cli` is) and its DSN/SES export is not the main routing path. Replaced in part on 2026-10-19 (decisions 1 and 3).
- **Upstream contribution:** not practised in six weeks (no upstream issue or PR filed, at least eight queued). Replaced on 2026-10-19 (below).
- **Geometry over vision: kept, sharpened.** The false "done" on openMPPT came from *sampled* geometry and was caught by the user by eye; the mounting-hole false alarm came from a wrong convenience property. Geometry means `kicad-cli` output and raw S-expressions, read as complete lists; a render for human review is encouraged but never evidence.
- **Narrow human-in-the-loop: replaced.** "A human reviews each autorouted proposal" did not stop a false done claim: the checkpoint existed and the claim still came from incomplete evidence. The machine-checked gate decides done; board class decides who routes power and zones; the dry-run plus revision-token pattern stays for any destructive mutation (decision 4).
- **kiutils (GPLv3) licensing: closed** (since 2026-09-02); `kicad-tools` covers schematic I/O under MIT.
- **Phased roadmap (Phases 0-7): wrong measure.** Phases 0-6 were all marked done, yet no board was ever finished. Replaced by the acceptance ladder (docs/TESTING.md).
- **Diagnose-and-retry routing loop graded by real DRC: grading kept, loop questioned.** Both routers' self-scores anti-correlate with DRC, but on openMPPT one attempt took the whole 90-minute budget, so the retries never ran. Retries stay bounded by wall clock; rung results decide whether the loop earns its complexity.

**2026-10-19 (paradigm review v2)**
- **`kicad-tools` file I/O with its high-level models as the mutation path: changed (ticket 06, facts in ticket 03; decision 1).** Its low-level `Document`/`SExp` API round-trips 8 of 8 files KiCad-equivalent; its 0.20.0 high-level models delete schematic content, leave pad angles stale and lose `pad.size`. 0.23.0 fixes some of that but cannot save on Windows; 0.24.0 saves again and persists pad edits (build ticket 71). Hard rule 1's stated reason ("KiCad relies on exact formatting") is false: KiCad reads tokens, not layout. Hard rule 1 keeps its ban and names the real silent failures; hard rule 2's cross-check moves into code as geometry readers on raw tokens. Build tickets 38, 39, 42-44.

Rung 1: KRT leaves 6 items on `/CC1`, `/CC2`, `VBUS` and `GND` unconnected (the USB-C pads); Freerouting leaves 3 items on `+3V3` and writes 2 GND `track_width` errors at 0.0952 mm. Rung 2: both connect all 34 nets (0 unconnected) and fail only on the 6 `silk_overlap` errors of the input floor, which no router can fix, plus under-width delivery (Freerouting in 5 of 5 attempts, KRT in 2 of 5). The measurement cannot rank them, so under the ROADMAP rule neither earns more integration work yet; rung 2 needs a ladder decision on its input floor first. DSN path: ticket 17, facts in ticket 16 (rung 2 in one round trip through KiCad's own exporter: 0 unconnected, against 125 with our DSN). Build tickets 36, 37, 46, 47.
- **Only the gate is evidence; no tool return value counts: kept for done and routed, extended (ticket 08, audit in ticket 07; decision 4).** 9 of 28 writing tools verified their write and 13 checked nothing. Some silent failures touch files the gate never reads (the lib-table wipe, the hierarchy collapse, the UTF-8 loss). Build tickets 22, 29-32.

KiCad's 36 demos cover every test area, `kicad-cli` position and IPC-D-356 exports agree with raw positions to within 0.0018 mm, and the demos exposed the `_outline_frame` arc bug at first contact. Demos are read from the install, nothing is vendored. Build tickets 34, 35.

Amended 2026-10-19 (owner, ticket 14): issues are filed without a per-issue review, after a duplicate check; pull requests and comments on other people's threads still need the owner. "Fork only if unresponsive" is dropped: the write layer removes the need for a fork. Build ticket 48.

## Decisions

1. **File I/O: `kicad_tools` (MIT, PyPI) parses and serialises, our own write layer mutates (re-decided 2026-10-19, `paradigm-review-2` ticket 06).**
   - Parsing and serialising use `kicad_tools`' low-level API (`Document`/`SExp`), which round-trips files KiCad-equivalent. Its generators (parametric footprints, courtyard geometry) stay in use.
   - Every mutation goes through a thin write layer of our own on that API. It handles quoting, `\r` escaping, number precision and pad angles on rotation. It saves through its own temporary sibling file, the tool's self-check (decision 4) and a per-file `kicad-cli ... upgrade --force` parse check, then `os.replace`. The high-level models' setters and `PCB.save` are not used for mutation.
   - The high-level models are allowed only for reads (under the hard-rule-2 cross-check) and generators. The one high-level write allowed is building test fixtures under `tests/` (docs/TESTING.md). Geometry readers that evaluate raw tokens in the right frame, proven against `kicad-cli` position and IPC-D-356 exports, become the sanctioned source for position facts (build ticket 43).
   - **The write layer exists (build ticket 42): `boardproof.write_layer`.** `save(root, path)` (any `.kicad_pcb`/`.kicad_sch`/`.kicad_mod`/`.kicad_sym` tree), `save_pcb(board, path)` (a `kicad_tools` `PCB`, replaces `board.save(path)`) and `save_project(data, path)` (`.kicad_pro` JSON) serialise with our own serialiser, write a temporary sibling in UTF-8, check it (`kicad-cli <pcb|sch|fp|sym> upgrade --force` on a scratch copy, any non-zero exit or crash code is a failure, every sub-sheet of a schematic checked on its own; a JSON read-back for the project), run an optional `verify(temp)` hook (where build ticket 22's verify-before-replace plugs in), then `os.replace`, retrying Windows' transient sharing denial (WinError 5/32) for up to 3 s with `commit_directory`'s schedule; the checks run once, before the first move (build ticket 78). On any failure the target is byte-identical. A check failure raises `WriteLayerError(code, ...)`, which names it; a failed move raises `os.replace`'s own OSError unchanged after the retry. The temporary file is removed with the same retry; if it cannot be removed, the error carries a note naming it. Typed atoms: `string`/`symbol`/`number` and `set_string`/`set_symbol`/`set_number` replace `SExp.set_value`. `load(path)` parses without newline translation. All 21 `PCB.save` sites and both `save_project` sites use it; a mutation with no MCP tool goes through the layer's typed setters and `save`, never through the high-level setters, `PCB.save` or raw text, and is reloaded and compared with the intended change. `commit_directory(temp_dir, target)` moves a verified revision directory into place (the six checkpoint tools that build one), retrying Windows' transient sharing denial for up to 3 s.
   - Always the newest `kicad_tools` release: 0.24.0 since build ticket 71 (0.23.0 from build ticket 42, adopted together with the layer's own save because 0.22.0+'s `PCB.save` and `save_project` fail on Windows). `pyproject.toml` carries only a floor (`>=0.24.0`). What each version changed for us is under "Known facts and gotchas" (`kicad_tools`), pinned per version by `tests/test_kicad_tools_facts.py`. 0.24.0's `PCB.save` works on Windows again and refuses edits it cannot persist; the layer stays the only save path all the same, because `PCB.save` writes LF where KiCad writes CRLF on Windows, writes `\r` raw, adds a top-level net table to KiCad 10 boards, and has no parse check, self-check hook or verified `os.replace` (build ticket 71).
   - Migration is incremental, not a big-bang rewrite (build tickets 38, 39, 42-44). By 2026-10-29 the write layer carries nearly every save (21 `PCB.save` sites moved in build ticket 42; 3 high-level saves remain in `tests/ratchets.toml`, together with a shrink-only list of raw writes). The losses of the old high-level path are listed under "Known facts and gotchas".
   - Never import `kiutils` (GPLv3).
2. **`kicad-cli` is the only verification authority.** That covers DRC/ERC JSON (`--format json --severity-all`), netlists and exports. Call `kicad_cli.ensure_kicad_cli_on_path()` before any `kicad_tools` call that shells out.
3. **Router backend = thin adapter; no fixed lead; the gate picks the winner per board. This supersedes the earlier "KRT leads, Freerouting cross-checks" (re-decided 2026-10-19, `paradigm-review-2` tickets 05 and 17).** KiCadRoutingTools (KRT, drandyhaas, MIT) and Freerouting (GPLv3, subprocess only) run as equals.
   - **Ranking:** set only after a fair re-measurement: Freerouting with a correct DSN, and the same rules for both, including the under-width check (build tickets 36, 46, 47). Build ticket 47 ran it under protocol 5 and could not rank them (0 of 20 attempts passed). The first official protocol-6 batches on rung 1 (2026-10-28) gave Freerouting 5 of 5 `PASS (necked)` and KRT 0 of 5, the latter from KRT 0.23.1 reading zero pads of the old board's footprint with unquoted pad names (build ticket 112; the board and checkout have since changed, see the pad-count table below); rung 2 cannot pass for either (build ticket 106). After that the ROADMAP rule applies: a backend that is never the one passing on any rung earns no more integration work.
   - **KRT feature work is paused** until that re-measurement. Only KRT work that blocks a measurement goes ahead (the under-width delivery, build ticket 37; the 0.23.1 snapshot, build ticket 33). The owner's goal that every KRT capability is used resumes once KRT is the router that passes on a rung.
   - **Freerouting's DSN path (ticket 17):** KiCad's own Specctra exporter and SES importer (`pcbnew.ExportSpecctraDSN`, `ImportSpecctraSES`), run in KiCad's bundled Python on a scratch copy of the board. `pcbnew` only ever writes the scratch copy. The routed result reaches the real board through the write layer (decision 1), by the same delta path KRT uses, with the self-check (decision 4) and the drift guard (decision 12). The import is graded by `verify_board`, never by its return value (it returns `True` even when it skipped items), and skipped-item counts are reported. Our `kicad_tools` DSN export, its text patches, our SES parser and the y-convention code are removed (build ticket 46). With KiCad 11, which removes SWIG, the path moves to `kicad-cli pcb export specctra` plus IPC `ImportSpecctraSession`; that becomes a build ticket once KiCad 11 is released.
   - The current KRT integration rules came out of real failures. Default to `--escalation board --no-fix-drc-settings`. Pin floors with a generated `--fab-overrides` (strictest class, `max()`). Copy the sibling `.kicad_pro`, `.kicad_prl`, `.kicad_dru` and lib tables into every trial directory. Never adopt KRT's rewritten `.kicad_pro`; restore the original before grading. Apply results as a delta through the write layer (decision 1), never through KRT's writer. Exclude high-fanout power and GND nets from routing and pour them instead. Route before pouring.
   - **Feature inventory:** the KRT feature inventory in the maintainers' research notes (2026-10-11, from a read-only clone, v0.23.0). It is the checklist for "every KRT capability is used", paused together with new KRT feature work (above). Reconcile it with the earlier `krt-capability-suite` survey (its tickets 01-04, 09). The tool list is generated from `krt_registry.py --json` (71 tools), with `krt_capabilities.py --require` pinning the version, so no feature is silently forgotten.
   - **Integration mode (decided 2026-10-11): CLI subprocess.** Spawn each tool with an `argv` list (never a shell string: every KiCad net name starts with `/`, which MSYS2 rewrites). Read the `--json` / `--json-out` outputs, and treat each output file as a new board revision, copied together with its sibling project files (`copy_board.py`). Use the native `--preview` / `--dry-run` for proposals. Do not import KRT as a library.
   - **Features most easily overlooked** (details in the inventory §5): `--layer-costs` for poured planes, `--force-reroute` / `--rip-existing-nets`, `--fab-tier` and `--strict-sizes`, `--keep-away`, the design brief and `check_floorplan.py --emit-intent` with `--intent` on every placement tool, `add_rule_area.py`, `place_fanout_clearance.py`, `--write-fill` / `fill_for_delivery.py`, `--schematic-dir`, `--preview` / `--undo` / `--group-by sheet`.
4. **Checkpoint mechanism.** Every mutation that is destructive, or whose result is not yet verified, follows propose, then a `revision_token`, then confirm, with bounded and TTL-limited pending state. It is implemented for component match, autoplacement, routing, placement optimisation and graphic removal. `register_library_asset` deliberately writes without a checkpoint, because it is deterministic; the self-check rule below still applies to it.
   - **Self-check (decided 2026-10-19, `paradigm-review-2` ticket 08).** Every tool that writes a KiCad file, checkpointed or not, verifies before it replaces: it writes a temporary sibling, reloads it and compares it with the intended change, and replaces the original with `os.replace` only on a match. On a mismatch the original is untouched, the temporary file is deleted, and the tool returns `ok: false` with code `write_not_verified` and a list of mismatches (expected, actual, file location). A passed self-check means only "the write landed"; it is never evidence of a finished board. Every self-check has a test that feeds it a corrupted write and shows it fires. Ratchet tests hold the line: a ban on pad `size`/`drill`/`layers` assignment, and shrink-only lists of raw writes, convenience-property reads on mutation paths and writing tools without a self-check. The mechanism lives once, in the shared checkpoint helper (build ticket 22); the rest is build tickets 29-32.
   - The checkpoint revision token carries the project's last-known composite hash (decision 12), which confirm and the drift guard check, plus a per-proposal id, so two proposals on an unchanged project do not collide. Built in `checkpoint.py` (build ticket 22: `Pending` issues `<project hash>-<proposal id>` and the confirm's drift guard refuses a changed project; five modules use it); the drift guard for non-checkpointed writes is still build ticket 40.
5. **Adapter modes.** `resolve_backend(mode)` returns either `IpcBackend` (live, so state is always fresh) or `FileBackend`. In `auto` mode it falls back to file *reads* only when the transport is unreachable, and it fails closed for mutations. File-drift detection is specified in decision 12 and **not built yet** (build ticket 40).
6. **External tools stay at arm's length.** Each is discovered in the same order: environment variable, then PATH, then a platform glob. A missing tool returns `status: incomplete` with install instructions, never a wrong answer. Licences were checked against each tool's LICENSE file: Freerouting is GPLv3 (subprocess), easyeda2kicad AGPL-3.0 (subprocess, core dependency), KiKit MIT (but it needs `pcbnew`, so it runs in KiCad's bundled Python as a subprocess and stays out of `pyproject.toml`), ngspice modified BSD (subprocess, use `ngspice_con.exe`), kipy MIT (imported), KRT MIT (subprocess), and the CDFER JLCPCB library MIT (index vendored). Konnect is AGPL plus commercial and serves as an ideas-only reference. Its dry-run token, lazy toolsets and naming conventions were adopted.
   - Other prior art: KiCAD-MCP-Server, kicad-mcp-pro, the Seeed MCP server, circuit-synth (MIT, no MCP server), atopile, Zener, tscircuit and SKiDL. None publishes a routed board comparable to openMPPT (maintainers' research notes, section 2). The full September survey is in the research notes at `3380b34`.
7. **Sourcing.** One `search_parts` merges results from every registered provider. Assets come from easyeda2kicad (by LCSC ID), the CDFER JLCPCB library, or `kicad_tools.library.generators` (parametric footprints). Datasheets are checked with `pdfplumber` before a part is committed. Part preference: JLCPCB Basic, then Preferred, never Extended for passives.
8. **Library portability.** Assets are written under the project tree, lib tables use `${KIPRJMOD}`-relative URIs, and `check_project_portability` audits them.
9. **Tool conventions.** Names are `snake_case` and verb-first. Units carry a suffix (`_mm`). ID types are disambiguated. Collections take the form `{count, items}` with pagination and a `CHARACTER_LIMIT`. Every tool carries MCP annotations. Errors appear in the result content. Verdicts are evidence-gated: a partial check returns `incomplete`, never a pass. A failed self-check (decision 4) is a demonstrated tool fault and returns `ok: false` with `write_not_verified`, not `incomplete`, which stays the gate's word for missing evidence. `load_toolset` must call `ctx.notify_tools_changed()`, because the SDK does not emit it.

10. **`verify_board` is independent of the router (decided 2026-10-11).** It is built on `kicad-cli` (`pcb drc --refill-zones` plus the unconnected-item report) and returns PASS/FAIL with the complete per-net lists. KRT's own checkers (`check_complete.py`, `board_score.py`, `check_drc.py`, `check_reachability.py`) run only as diagnostics that explain a failure. A disagreement between them and `kicad-cli` is itself a FAIL signal, because KRT parses and writes boards with its own code and would otherwise be grading itself.
11. **What counts as "autonomous pass" (decided 2026-10-11).** A rung is passed autonomously when, with no human intervention, the best of at most N = 5 attempts (varied seeds or router strategies) inside a fixed wall-clock budget per rung passes the gate. The attempt count and the success rate across all attempts are always reported, so a 1-of-5 board is visibly different from a 5-of-5 board. The exact per-rung time budget is set when the rung's ticket is written (starting point: 30 minutes).
    - **Protocol detail (2026-10-11, pivot-ladder ticket 06):** a frozen manifest and attempt plan before the board is seen; every attempt starts from the identical input; levers are only the pre-declared plan's discrete settings (escalation, grid step, max-iterations, ordering strategy; KRT has no seed lever); results are reported per backend and never pooled; any human touch relabels the run "assisted", detected by hash and log; every batch is appended to an index and a rung's result is the first scored batch on that protocol version. Router runtime is unmeasured, so the 30-minute budget is provisional.
12. **Copilot hand-off is file-based (decided 2026-10-11; kept, and the drift guard specified, 2026-10-19, `paradigm-review-2` ticket 11).** The agent prepares a revision (placement, signals, checks) and hands it over through the checkpoint mechanism (decision 4). The human edits power routing and zones in KiCad, saves and closes the file, and the agent reloads, verifies and continues. Live IPC stays out until the file hand-off proves to hurt in practice: kipy 0.8.0 live schematic reads are broken, and the gate and the self-checks judge files. The existing `copilot` IPC toolset stays as it is, but the Copilot hand-off does not depend on it. The drift guard (P1-19) is **not built yet** (build tickets 40 and 41). Its contract:
    - **What is hashed:** one last-known composite hash per project over every file a tool reads or writes (`.kicad_pcb`, `.kicad_pro`, `.kicad_dru`, the `.kicad_sch` files), using the gate field's hashing in `gate_state.py`.
    - **When it changes:** only after a write whose self-check passed (decision 4), or by an explicit reload call. Never otherwise, so an unchecked write can never be re-hashed into looking legitimate (mixelpixx #244).
    - **When it is checked:** before every write, not only in checkpoint pairs. The checkpoint revision token carries this hash (decision 4).
    - **On drift:** the tool refuses with `drift_detected`: the changed files, the known and current hash of each, and the instruction "reload, then re-propose". It never re-proposes by itself, because that would lay the agent's plan over human edits it has not seen. There is no `force` override.
    - **Log:** every drift refusal and every reload is one line in a project log (time, files, hashes).
    - **KiCad open:** while KiCad's lock file for a file exists, writing tools refuse with `file_open_in_kicad`, naming the file. Reads stay allowed. A stale lock file (after a crash) is reported, never deleted automatically.

14. **`verify_board` contract (decided 2026-10-11; pivot-ladder ticket 03 holds the full text; docs/TESTING.md has the gate's contract).**
    - Verdicts are `PASS`, `FAIL` and `INCOMPLETE`, with `FAIL` first. `FAIL` means the board is demonstrably bad; `INCOMPLETE` means the evidence is missing.
    - It grades against the board's own rules plus a pinned baseline of `rule_severities`, `.kicad_dru` `severity` clauses and netclass limits. Any deviation is `INCOMPLETE` until a human re-baselines. There are no waivers.
    - Each verdict is three `kicad-cli pcb drc --refill-zones --severity-all` runs on fresh copies, de-duplicated, with union semantics (any error in any run is `FAIL`).
    - Guards that give `INCOMPLETE`: `kicad-cli` failure, a missing or unannotated schematic, a count at exactly 199 or 499, a rules deviation.
    - It is always loaded (start toolset). Every other tool that returns a board state carries `gate: {verdict, board_sha, age}`, and only `verify_board` may say "routed" or "done". `pcb_run_drc` is rebuilt to include unconnected items.

## Known facts and gotchas

- **Repeated kicad-cli runs in the test suite: upgrades repeat, netlist, ERC and DRC runs almost never do (issues 172 and 176).** Counted over the whole suite with a hook outside the repository: 62 percent of the `sch upgrade` runs and 42 percent of the `pcb upgrade` runs had an input identical to an earlier run, while `sch export netlist` (32 of 6886), `sch erc` and `pcb drc` runs (none) almost never did. That is why the write layer memoises the schematic parse check per distinct sheet content (key: sha256 of the bytes, kicad-cli path, size and mtime, the `KICAD*` and `KIPRJMOD*` environment; `tests/test_load_check_memo.py`) and why the opt-in test replay (`BOARDPROOF_CLI_REPLAY=1`, `tests/_cli_replay.py`) caches only upgrade and version runs. A replayed run returns paths in the native (backslash) form on Windows even when kicad-cli wrote slashes. Evidence: `tests/test_load_check_memo.py`, `tests/test_cli_replay.py`.
- **KiCad 10 field rules, measured with `kicad-cli sch export netlist --format kicadxml` (issue 167; pinned in `tests/test_kicad_field_rules.py`; source reading in `docs/research-kicad-symbol-placement.md`).** Fixtures come from the tools (`project_create`, `add_symbols`, `create_sheets`) plus the write layer on `kicad_tools`' S-expression API for the states no tool writes (a version number, a literal `~`, a lowercase property name, a bare `hide`). (1) `"~"` in `Datasheet` or `Footprint` is read as empty when the file version is below 20250318 (20250317: no `<datasheet>`, no `<footprint>`) and is literal text from 20250318 on (20250318 and 20260306: the netlist has `<datasheet>~</datasheet>` and `<footprint>~</footprint>`). `add_symbols` writes its files at version 20231120 with `Datasheet "~"`, so there `~` is empty. (2) Multi-unit part, `Footprint` or `Datasheet` empty on one unit and filled on another: unit 1 empty and unit 2 filled gives unit 2's value; both filled gives unit 1's; unit 1 filled and unit 2 empty keeps unit 1's; `Value` follows the same rule. With units 1 (empty), 2 (B), 3 (C) the winner depends on the order of the symbols in the file: 1,2,3 gives B; 1,3,2 gives C; 2,1,3 gives B; 2,3,1 gives C; 3,1,2 gives C; 3,2,1 gives B. So it is not "the lowest unit with a value"; a writer must fill the field identically on every unit. One reference on two sheets (units 1 and 2 on different sheets, one reference): the lowest unit with a non-empty value won in all four cases measured (1 empty/2 filled gives unit 2's; 1 and 2 filled gives unit 1's; unit 2 on the root and unit 1 on the child, both filled, gives the child's unit 1; the lower unit empty gives the other). (3) A property named `footprint` (lowercase) in a 20260306 file is read as the Footprint field (netlist `<footprint>` and `<field name="Footprint">` carry its value); a user field `Lcsc` stays a separate field and does not become `LCSC`. (4) `(hide yes)` as a direct child of `property` loads; a bare `hide` or `(hide)` there fails the load (`kicad-cli` exit 3, "Konnte Schaltplan nicht laden"); inside `effects` a bare `hide` and `(hide yes)` both load. The write layer's save-time parse check refuses a bare property `hide` and leaves the file unchanged. Evidence: KiCad 10 kicad-cli on this machine, `tests/test_kicad_field_rules.py` (25 tests).
- **PDFium (pypdfium2, behind pdfplumber's `to_image`) is not thread-safe and a fault in it ends the whole server process (issue 104).** Two parallel `render_schematic_diagnostic` calls with `png_dpi` died with `Windows fatal exception: access violation` in pypdfium2's `page.render`, and both callers saw `Connection closed`; FastMCP runs sync tools on worker threads. The PNG step now runs in a child process (`python -I src/boardproof/_png_worker.py`, own temp dir, 120 s timeout, killed on timeout) behind a process-wide lock (`png_render.PDFIUM_LOCK`); a crash or timeout gives `refusal: png_render_failed` with the SVGs (and the PDF) still returned. The only other PDFium user, `inspect_datasheet` page images (`sourcing/datasheet.py`), runs the same way since issue 105: `png_render.render_pdf_regions` starts `python -I src/boardproof/_png_crop_worker.py` (one child for all regions of a call, the crop box per region passed as an argument, same lock and 120 s timeout). A crash, timeout or unusable output keeps the whole PNGs that were already written, lists every other page under `pin_numbering.page_images_failed` with its reason, and makes the tool result `status: "incomplete"` with `refusal: "png_render_failed"` (the extracted tables stay in the result). No PDFium call is left in the server process. `pdfplumber` text and table extraction is pdfminer, pure Python, and does not touch PDFium. A failed move takes back the PNGs it already moved, but a PNG that already existed under the same name in the output directory is overwritten by the move and is not restored. Pinned by `tests/test_diagnostics_toolset.py`.
- **The adoption render check judges where the model sits in Z by its silhouette below the board's bottom face (issue 116).** `confirm_adopt_parts` renders the footprint with and without its model and compares the silhouettes. An SMD footprint may sink 0.1 mm (`MAX_SINK_MM`). A footprint with a raw `thru_hole` pad (not `np_thru_hole`) has pin tails of any depth (measured on stock KiCad 10 parts: 0.3 mm radial capacitor, 1.4 to 1.8 mm pin headers, DIP and RJ45, 2.3 mm Phoenix terminal, 4.8 mm horizontal TO-220, 7.6 mm TO-3, 8.2 mm vertical TO-220), so depth is not judged there: the widest row of the silhouette below the bottom face may be no wider than the footprint's `thru_hole` pads side by side along X (union of the raw `(at)`/`(size)` extents, rotation included) plus `TAIL_MARGIN_MM`, otherwise the check fails and says which row, how wide, against what bound. A through-hole footprint is rendered on a board at least `THT_BOARD_MIN_MM` wide so that tails up to about 8 mm are not cut off at the image edge. What it does not catch: a body that sits on the top face and is shifted down by less than the board's thickness is still inside the slab (a silhouette cannot see it); a connector whose plated tabs make the bound wider than the shifted body (Molex 9346520x RJ45 shifted 5 mm: widest row 16.3 mm against 17.3 mm); a tall model shifted so far that it fills the whole render is `incomplete`, never a pass. A column test (every pixel below the board inside the pad columns) was tried and dropped: the render's horizontal mapping did not match the pad coordinates on unshifted stock parts. Pin-to-pad matching (symbol pin count against footprint pads) is not part of it and is a separate check to build. Measured on 24 stock parts in the review of ticket 116: the width rule does not see a 5 mm shift on TO-220 and TO-247 vertical, TO-39 and RJ45 (wide plated tabs or metal cans), nor a 3 mm shift on TO-92 and LED (the stand-off hides it); a shift up to the board thickness (1.6 mm) is invisible for every part; a model is judged only against the slab, and the evidence images stay the human check.
Evidence references are old ticket IDs at `3380b34`, test files, or the maintainers' tickets, cited by number.

Decisions: with no selector every placed symbol of the sheet is picked (child sheets are not followed); "unconnected" has no hidden-pin guard of its own (measured: KiCad ties the hidden pins of a part by name into one net, e.g. the hidden GND passives of `74xx:74ALVC164245` share one `Net-(U2-GND-Pad10)`, so they are never listed open; an isolated hidden pin on an open net would be marked; the `hidden` flag backs only the explicit refusal as `pin_hidden`; a named pin tied to a hidden one is refused as `pin_connected`), pins of type `no_connect` (naming a visible one, e.g. `Interface:SLB9660xT` pin 9, gets a marker and ERC does not change), the result keeps each pin `type` and counts under `silenced_other_erc` the `input` and `power_in` pins whose `pin_not_driven` / `power_pin_not_driven` the marker also silences (measured on `BD15GA5WEFJ` pin 2: pin_not_connected 5 to 4, pin_not_driven 2 to 1), pins of type `no_connect` and `#` power symbols (a floating power symbol still shows `pin_not_connected` and `power_pin_not_driven` in ERC: that is a missing wire, not an open pin), and naming a hidden pin or a power symbol pin is refused (`pin_hidden`, `power_symbol_pin`). Power symbols are not in kicad-cli's netlist, so their pins cannot be classified at all. A sheet used more than once and an unannotated reference are refused as `pin_not_in_netlist`. `sheet_editing.Sheet` gained `erc_for` (ERC census of the project from a scratch copy with the edited tree) for this check.
- Changing label and free text (issue 114, `sheet_editing.set_text`): the text is the first string atom of a `label`, `global_label`, `hierarchical_label` or `text` node, and `write_layer.set_string(node, 0, ...)` replaces it with uuid, `(at ...)`, shape and effects untouched (`tests/test_set_text.py` compares the other children serialised before and after). A renamed hierarchical label does not rename the sheet pin of the parent's sheet symbol; the result lists `pin_name_mismatch` (the pin keeps its old name) and the two stay apart until `remove_sheet_pins` and `add_sheet_pins` rename the pin. - Instance data of new symbols is never reported clean when unproven (issue 187): `_reattach_to_tree` (add_symbols, and add_labels when a spec is kind power; wires, junctions, labels and no-connects hold no instance data) used to return the text unchanged and say nothing when `find_root` failed, the tree had problems or the walk raised, so the call said ok with own-uuid paths KiCad later calls stale. - **kicad-cli drops a unit's pins silently (build ticket 83).** kicad-cli 10 leaves out every pin of a unit whose body is missing from the sheet's embedded lib symbol, with exit 0: on jetson, removing J1 unit 2's body from som_io2's embedded symbol dropped 68 of 68 pin nodes while J1 stayed listed and the unit count was unchanged. kicad-cli gives every other pin a node: an unconnected pin gets a net of its own, and stacked pins share one. The import scan therefore checks a unit on another sheet pin by pin against the netlist's `(reference, pin)` nodes. vme-wren's IC14 sits on 9 sheet uses, not 11.
- **kicad-cli reads instance paths as id vectors (build ticket 73).** With several `(path ...)` entries at one sheet use, kicad-cli 10 takes the LAST one, whatever its project name. It reads a path in any case, between any number of slashes (leading, trailing, doubled or none), and reads each segment as a canonical uuid, 32 hex digits, either of those in braces, or an 8-digit legacy timestamp (`1234abcd` is `00000000-0000-0000-0000-00001234abcd`). Spaces, `urn:uuid:`, other lengths and wrong hyphens are read as no live path. A legacy timestamp is 1 to 8 hex digits, zero-padded (`abc` is `00000abc`; `path_key` accepts only 8). A segment that is not hex (`root`, `zz`) matches nothing, not even the identical string as the sheet's own `(uuid ...)`: a hand-made fixture with `(uuid "root")` and the path `/root` has a stale entry, not a live one (build ticket 95, measured with a last-entry-wins probe). A KiCad 6 `symbol_instances` table is read only in a version-20211123 file. `sheet_tree.path_key` encodes exactly the measured forms and refuses the rest.
- **kicad_tools' S-expression reader is not KiCad's lib-table reader (build ticket 76).** kicad_tools unescapes backslashes (`"D:\Data\x"` reads as `D:Datax`), takes `#` and `;` as comments and splits a token at `\v`; KiCad 10.0.7 does none of this. KiCad 10.0.7 does not unescape lib-table strings (measured: `(descr "a\"b")` skips the table, `(descr "a\")` loads); its development branch does, so a backslash in a table means different things to the two. The library toolset therefore reads `fp-lib-table`/`sym-lib-table` with its own reader, checked against kicad-cli on 92 table variants.
- **On Windows a wait timeout does not count standby (build ticket 88).** `subprocess.Popen.wait(timeout=...)` waits with WaitForSingleObject, whose timeout has not counted time in sleep or hibernate since Windows 8. A gate run with a 4200 s suite timeout ran 5331 s and ended GREEN; the System event log (Kernel-Power 42/105, Power-Troubleshooter 1) shows 3770 s of standby inside it. `batch_gate.default_runner` therefore measures its deadline with `time.time()` and waits in 5 s slices. `subprocess.run(timeout=...)` has the same blind spot.
- **Net classes are resolved from a measured allowlist (build ticket 36).** KiCad 10's net-class matcher and Python's `re` differ: KiCad expands a vector at the end of a pattern (`D[0..3]` classes D0..D3) as a bus, a bus-vector or brace net is classed through its members, and KiCad's `.`, `*` and `?` match a line break. Three fixes that patched one difference at a time each failed open. `board_rules` therefore resolves a class only for the pattern syntax checked against KiCad's `GetEffectiveNetClass` (`_pattern_syntax_problem`) and refuses the rest, and refuses a net holding a control character while any pattern or assignment exists. `D[0-3]` is a plain character class in both.

- **The MCP SDK drops unknown tool arguments silently (build ticket 69).** FastMCP builds each tool's argument model from the function signature and ignores keys it does not know, so a misspelled or invented argument returns ok as if it were applied. `generate_footprint` refuses them by replacing the registered tool's `fn_metadata.arg_model` with a subclass that names every extra key (`toolsets/sourcing.py` `_refuse_extra_arguments`, reached through `mcp._tool_manager.get_tool`, which has no public accessor). - **`inspect_datasheet` returns text tables only; a package's pin numbering needs `package=` (issue 39).** Before the change the tool ran `pdfplumber` table finding over page text and classed a table as a pin table when the first 400 characters of its page contained "pin": no link to a package, and a pin diagram drawn as an image or vector gave `no_structured_tables_found` (checked on a synthetic one-page PDF whose pin drawing carries no text; the vendor PDFs listed in tests/fixtures/README.md are not in this tree, so no vendor datasheet was run). With `package="SOT-23"` the result now has `pin_numbering`: `machine_extracted: true` with the pins only when a table with recognised Pin and Name headers sits directly under a line naming that package (so SOT-23 does not match a SOT-23-5 heading); anything else is `machine_extracted: false` with a reason and, given `image_dir`, PNG renders of the candidate pages (cropped to embedded images, else the full page). Nothing is OCRed or inferred; the gate that consumes it (not built) must treat `false` as unverified. Rendering uses `pdfplumber`'s own `to_image` (pypdfium2 and Pillow arrive with it), no new dependency. Refused as unverified (review of the first commit): a heading naming a second package or other words than pin-table vocabulary ("SOT-23, SOT-89 ...", "Not for SOT-23 use"), a package name that is the tail of a longer token ("23", SOT-23-5), numeric pin ids that are not 1..N (a gap or a truncated list), a table followed on the next page by ANY pin-like table, whatever heading it sits under (review rounds 2, 4 and 5; every pin-like table on the next page counts, not only the first, and the first three rows of each are examined so a title row above the header does not hide it; pin-like is wider than the parser: ids such as a3, 3A, A1B, EP, 3. or four digits, a blank leading cell, headers Pin Name, Pins, Pin/Pad, Terminal; a table of empty cells, an ordering table or a Name/Function table does not count. Next-page check (issue 46): the three pages after the table are searched, every row of each table is examined (a header on row four is found), a column holding pin-like ids in two rows counts (name-first headerless tables), ids such as P1.0, 1,2, 1-3, five digits and full-width digits are pin-like (cells are NFKC-normalised), and a rotated page is read with a looser rule because pdfplumber returns its grid transposed, with reversed rows and reversed character order (checked at 90, 180 and 270 degrees on synthetic pages). Known continuation limits, not handled, all giving true: limit C1, a pin table more than three pages after the first one is not seen; limit C2, a pin table drawn as an image, or as text without ruled cells, is not seen, nor is a rotated table that pdfplumber does not find; limit C3, a loose rule on rotated pages and the id-in-two-rows column rule trade false positives (a numeric spec table may block) for fail-closed behaviour. Round 4: a heuristic that recognised other packages failed open on headings such as "SC431 Pin Functions (continued)" or "... DBV (SOT-23-5L)", so it was removed; a datasheet with one pin table per package on consecutive pages therefore gives unverified plus page images, accepted as the price of failing closed), pin or name cells with a newline or an unmapped glyph, and a blank package name. An embedded image is used as the crop only when the images cover at least a quarter of the page, else the full page is rendered. Known limit: `machine_extracted: true` means a table was found under a heading naming the package, not that it is complete; a list cut at the tail with no following page, or a continuation the next-page check cannot see, still gives true. The PNG is written to image_dir/<pdf stem>_p<page>.png in exclusive-create mode and never replaces an existing file: when the name is taken by other content, _2, _3 ... is appended, and a file with identical bytes is reused (issue 46). Open (limit G1): the gate that consumes `machine_extracted` (refuses a symbol whose pin numbering is unverified) is not built; nothing in `src` reads the flag yet, so the refusal rests on the tool description and the sourcing skill until a gate ticket owns it. A table whose heading is not the line directly above it also comes back unverified rather than guessed.

- **Two tool calls writing one file at once lost an update, and the schematic tools raced on a shared temporary name (issue 87).** Every tool reads the file, changes it and saves, so add_symbols and add_wires in one response both loaded the old sheet and the second replace dropped the first one's change; the four schematic tools also wrote the one fixed name `<sheet>.utf8.tmp`, so the overlap surfaced as `[WinError 5]` (reproduced in `tests/test_write_serialised.py`: red without the lock with a `WinError 2` on the second `os.replace`, green with it). The fix: `write_layer.path_lock` holds one re-entrant in-process lock per normalised absolute path across the whole call of a sync, non-read-only tool registered through the wrapper `gate_state.attach_gate_field`, over the paths named by `pcb_path`, `sch_path`, `project_dir` and `path`. The schematic tools' replace now goes through `write_layer.replace_file` (the layer's retry of a transient WinError 5 or 32 for up to 3 s); a denial that outlasts it is the refusal `file_busy` (`ok: false`, nothing changed), which `as_lock_refusal` and the wrapper both answer. The lock guards against other calls of this server only (KiCad and other programs are the lock-file guard's business, issue 68); a call waits at most `LOCK_TIMEOUT_S` (60 s) for a lock another call holds (a Freerouting run holds it for minutes), then is refused with `file_busy` (`never_started`: it read and wrote nothing). Known limits, not covered: `async` tools (none takes a file path today), gate and core tools registered before the wrapping, a tool that writes a path not named by those four arguments, a parent folder and a file inside it (different lock keys), and symlinks or 8.3 short names (not resolved, so two spellings of one file are two locks). A bare WinError 5/32 that escapes a tool is reported without the claim that nothing changed, since a multi-file tool may have written other files first; `replace_file` and the timeout keep it, because there the file is provably untouched.
