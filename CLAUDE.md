## Project, as of the 2026-10-11 pivot

Boardproof is a Python MCP server (`src/boardproof/`, a suite of several thousand tests; `python -m pytest --collect-only -q -m "not network"` prints the current count) that automates KiCad PCB work: sourcing, schematic, placement, routing, verification and manufacturing export. **Rung 1 has boards with `PASS (necked)` from the gate (official batches under protocol 6: Freerouting 5 of 5; a PASS with forced necks, counted and labelled, never a plain PASS). No plain PASS exists yet, and the rung-1 board changed afterwards (protocols 7 and 8) and has no official batch under the current protocol.** One earlier run on openMPPT claimed "routed" and was wrong. The product promise is therefore tiered by board class. The **Copilot tier** is the default. The **Autonomous tier** is earned one board class at a time by passing the acceptance gate on the acceptance ladder.

## Hard rules (no exceptions)

1. **Never hand-edit KiCad files.** `.kicad_sch`, `.kicad_pcb`, `.kicad_sym`, `.kicad_mod`, `.kicad_pro` and `.kicad_dru` are never patched with Read/Write/Edit/sed, not even for a "small fix". KiCad reads tokens, not layout, but a text edit easily breaks what it does depend on: a raw line break inside a string silently drops a whole sub-sheet, a reordered token makes pads lose their nets with no error, an unquoted number or an unknown token fails the load, and pad angles are stored board-absolute. Make every mutation through this project's MCP tools, or, where no tool exists yet, through the project's write layer on `kicad_tools`' low-level S-expression API. Never mutate through the high-level models' setters or `save`. Do not write raw text.
2. **Never trust `kicad_tools` position or geometry convenience properties without cross-checking.** `Pad.position`, `Footprint.position` and `Zone.polygon` have all returned board-absolute coordinates that were wrong by the board/page origin. `pad.size = (...)` is silently not saved. Each of these has already led to a confident false claim, including "mounting holes 30-90 mm off the board" when they were not. Before you state, act on or report any position or geometry fact, read the raw `(at ...)`, `(size ...)` or `(polygon ...)` S-expression, or cross-check against it. Never base a mutation on a convenience property alone.
3. **Never call a board routed or done without a `verify_board` PASS.** The PASS must come from the acceptance gate (docs/TESTING.md): one machine-checked verdict with zero unconnected items on every net, zero error-level DRC, and all zones filled and verified. All figures come from `kicad-cli` output. Samples, category counts, "0 shorts", a router's self-reported score and `kicad_tools` properties are never evidence of done. `verify_board` exists (`src/boardproof/verify_board.py`, always loaded). Only its `PASS` counts; `FAIL` and `INCOMPLETE` never do. Without a PASS, make no routed or done claim at all. Report the complete per-net unconnected list and the complete violation list from `verify_board` (or from `kicad-cli pcb drc` when the gate cannot run) instead.
4. **openMPPT is frozen** until ladder rungs 1 and 2 pass. Do not route, place or "fix" it. The board lives in a separate repository (the MPPT hardware project, which is not part of this repo), branch `hardware/PCB_v1.3`.

## Working convention

- **For outside readers:** planning lives in the GitHub issues of this repository, which may be public; there is no private planning folder. Public docs state a fact in words and cite a ticket as a plain reference (for example "build ticket 112"); an issue migrated from the old planning records starts with "formerly build ticket N". The glossary in `docs/CONTEXT.md` explains ticket, map and protocol. The old backlog ids resolve through the maintainers' archive and may not be resolvable from a public copy.
- **Planning and tickets are GitHub issues** (`docs/WORKFLOW.md`). A map is one issue labelled `map` with a task list of its tickets; a ticket is an issue labelled by type (`build`, `research`, `decision`, `task`) plus `critical`, `parked` or `needs-owner` where they apply, with `Blocked by #n` lines; its status is open or closed, and its Answer and review verdicts are comments. Read and write them with `python scripts/issues.py` (`show`, `create`, `comment`, `close`, `list`), which refuses any text that `scripts/check_publishable.py` flags. Write every issue and comment so that it may become public: facts only, no real name, no machine path, no candid judgement of a person or another project. Chart a map (a planning method; the Wayfinder skill is one way) for any effort too big for one session, and do not presuppose the answer. The ticket IDs that code and older tickets cite (P1-xx to P5-xx, M-0x) resolve through the maintainers' archive.
- **Work a map's frontier in parallel.** Dispatch each unblocked, unclaimed ticket as its own subagent. Each build ticket runs on its own branch `ticket-<n>` in its own worktree, branched from the current local `main`: the plugin's builder creates the worktree from a fresh `origin/main`, so the coordinator pushes `main` and checks that `main` and `origin/main` are one sha before every dispatch (P5 below). Planning and research tickets need no worktree: they live in issues and their comments. Brief each agent with the acceptance criteria, the contracts it must follow (`ToolsetBuilder`, `SourcingProvider`, the checkpoint helper with its self-check and drift guard) and its file ownership. Give genuine encouragement in dispatches, not only specs.
- **Every build ticket gets an adversarial review.** `docs/dispatch/review-rules.md` holds the review rules: what a finding blocks, the delta loop and the stop rule. In short, every finding is classed BLOCKS or FOLLOW-UP, and CLEAN means no BLOCKS finding. A BLOCKS finding becomes a failing test before its fix. A FOLLOW-UP that is a pure fix is fixed in the same ticket before the merge (`docs/dispatch/review-rules.md`, "What a finding blocks"). Re-review the delta until the verdict is CLEAN; stop after the third delta review and escalate. The stop rule never permits a merge without CLEAN. Then, when the change touches behaviour, tool text an LLM reads, pins or protocols (otherwise targeted tests; see the commit bullet below), run the full suite from the worktree root with the shared interpreter by absolute path (`<main checkout>/.venv/Scripts/python.exe`) and `PYTHONPATH=<worktree>/src`; the run counts only if `boardproof.__file__` lies inside the worktree and pytest's `rootdir:` line names the worktree, because the shared `.venv`'s editable install points at the main checkout. The coordinator squash-merges the branch into local `main` only when the review is CLEAN, `git rev-parse ticket-<n>` equals the reviewed sha recorded in the ticket, and no test fails outside the known-red list. The verdict, the reviewed commit and the review text go into the ticket as comments on its issue. A change to critical-class text (`CLAUDE.md`, `docs/CONTEXT.md`, `.claude/skills/**`, tool descriptions) needs a CLEAN adversarial review before it is committed, even from a planning ticket.
- **Record findings immediately** in docs/ARCHITECTURE.md's known facts, the ticket's Answer (an issue comment) and one line in the map issue's Decisions-so-far.
- **Commit after every closed ticket and push right away**, without asking (durable owner authorisation, 2026-10-19). This holds for every commit on `main` and every research branch. Never force-push, never delete `main`. Run the full suite first when the change touches behaviour, tool text an LLM reads, pins or protocols, and once at each milestone such as the export (owner rule of 2026-10-29, docs/TESTING.md, "Test suite"); never run it twice for one logical change. A change that only moves files or edits docs, comments or docstrings gets review plus targeted tests instead, but edits to critical-class text (`CLAUDE.md`, `docs/CONTEXT.md`, `.claude/skills/**`, tool descriptions) are not "docs" for this purpose and need the full suite (`KICAD_DEMOS_REQUIRED=1 KICAD_ROUTING_TOOLS_REQUIRED=1 .venv/Scripts/python.exe -m pytest -m "not network" -q`). Known reds are only the entries of `scripts/known-red.txt` (P11 below); adding one needs its own ticket and a review, and any other failure blocks the commit or merge. Name the known reds that failed in the commit. There is no hosted CI (owner decision 2026-10-19: no paid GitHub), so this local run is the test gate.
- **A rule that was broken once becomes a test or a hook.**
- **Batch tools, not one-item-per-call.** Tools operate on collections and patterns ("place all decoupling caps", "fix every violation of type X"), not on one item per call. This is a project requirement.
- **Ask the user only when truly blocked**: credentials, accounts, or a scope or direction call. Otherwise make the call, write the reasoning into the ticket, and keep moving.
- **Don't over-wait.** If a long-running job passes about 3x its expected duration, stop it and escalate (for the batch gate, the stop point is the worst case it prints at its start; its own timeouts bound every step: docs/TESTING.md, fork playbook P11). Do not wait silently for hours.
- Use the `mcp-builder` skill when defining tool schemas.

- P4: n/a (nothing runs in production; a release is a commit or a local squash merge on `main`, P12).
- P9: The safety path is false claims about a board: hard rules 2 and 3. Unknown, absent, unparsed or unreachable means incomplete, never pass. Measurement protocol: the first OFFICIAL scored batch per (rung, backend, protocol sha) is the reported one; unofficial batches are shown beside it and never fill the slot; no re-run to improve an outcome; Freerouting is reported UNAVAILABLE rather than invented.

## Enforcement table (P8)

| Rule | Enforced by |
|---|---|
| "Routed" or "done" only from a `verify_board` PASS | `verify_board`; every board-state output carries `gate`; a sweep test fails on any other "routed" or "done" |
| No test seam (`drc`, `router`, `fill`, `connectivity_check`, `footprint_dirs`, `netlist_exporter`, `_clock`, `**kwargs`) reachable from the MCP surface | AST source-scan guard |
| An unofficial run (dirty tree, injected seam, unpinned rung, edited plan) never fills the official slot | `rung_runner.py` checks and their tests |
| Geometry and hard rules 1 and 2 in code | `tests/test_ratchets.py` with `tests/ratchets.toml` (a site your change adds needs a reviewed entry with a note) |
| Pushes: no non-fast-forward update, no deleting `main`, no mirror push | `scripts/git-hooks/pre-push`, installed into the common git dir (`cp scripts/git-hooks/pre-push "$(git rev-parse --git-common-dir)/hooks/"`, a merge step whenever the hook changes; the batch gate prints whether the installed copy is current) |
| Agent shells: force pushes, deleting `main`, switching the pre-push guard off | `scripts/git_guardrails.py`, a PreToolUse hook in `.claude/settings.json` for `Bash\|PowerShell\|Monitor` (not the plugin's `git-guardrails-claude-code`, which blocks every push) |
| Lint, tests, skips, known reds | `scripts/lint_gate.py`, `scripts/batch_gate.py`, `scripts/known-red.txt`, `scripts/known-skips.toml` |
| Instruction only | no hand-edits of `.kicad_*`; the `kicad_tools` geometry cross-check (moving into code: ratchets, build ticket 29; raw-token readers, build ticket 43); openMPPT frozen |
| Decided, not built yet | every writing tool's self-check (build tickets 22, 30-32), the drift guard (40), the KiCad lock-file guard (41) |

The guards defend against accidental or careless destructive commands by an agent, not against deliberate obfuscation (coordinator decision, 2026-10-20); the scope and what the hooks cannot see are in `docs/HISTORY.md`. There is no hosted CI and no server-side branch protection (owner, 2026-10-19): the local gate is the test gate.

## How to dispatch (P5, P6, P7, P10, P11, P12)

- P5: Up to about 5 builders on disjoint `Files:` lists; tickets that share files run in sequence. Agents are `playbook:builder`, `playbook:reviewer` and `playbook:researcher` (rules in `docs/dispatch/`), resumed with `SendMessage` for fixes; `general-purpose` only for ops work. Builder model: `env.CLAUDE_CODE_SUBAGENT_MODEL` in `.claude/settings.json`, `sonnet` (owner's standing rule for sub-agents). The reviewer's model: see the dispatch; the coordinator passes `model` explicitly for reviewers when the rule "reviewer at least as strong as the builder" needs a stronger one, and verifies the model of the first plugin dispatch. Every build ticket runs on its own branch `ticket-<n>` branched from the current local `main`: the plugin's builder makes its worktree from a fresh `origin/main` (its `WorktreeCreate` hook, under `$PLAYBOOK_SCRATCH/work/`), and local `main` is pushed after every merge (P1), so before each dispatch the coordinator checks that `git rev-parse main origin/main` prints one sha and pushes first if not. Planning and research tickets need no worktree. Every sub-agent runs its own tests before it reports.
- P6: Tests: `<main checkout>/.venv/Scripts/python.exe -m pytest <paths>` (never `pytest.exe`: collection fails on `from tests. ...` imports), without `-q` for counted runs, from the worktree root with `PYTHONPATH=<worktree>/src`; the result counts only if `boardproof.__file__` lies inside the worktree and pytest's `rootdir:` line names it. Targeted runs: small separate background runs (each aimed at under about 20 minutes, own log outside the worktree, own summary line, wait for the notification; `tail -15` the log). Lint: `scripts/lint_gate.py` (ruff pinned in the dev extra, `--config pyproject.toml --ignore-noqa`, shrink-only baseline `scripts/ruff-baseline.json`; a new finding is fixed, never baselined, `--shrink` lowers the baseline). Hand-back check: `env.PLAYBOOK_BUILDER_CHECK` in `.claude/settings.json` runs `scripts/builder_check.sh` (lint plus the guard tests, under 9 minutes). Scratch: `env.PLAYBOOK_SCRATCH` in the uncommitted `.claude/settings.local.json`. Bash tool: no long heredocs with apostrophes; write files with the Write tool. Details: `docs/dispatch/builder.md`, Tests.
- P7: critical: `verify_board.py`, `gate_state.py`, `kicad_cli.py`, `rung_runner.py`, `rung_backends.py`, `autonomy_run.py`, `autonomy_protocol.json`, `input_prep.py`, `schematic_import.py`, `board_rules.py`, `board_outline.py`, `silk_minimums.py`, `pour_step.py`, `routers/kicad_routing_tools.py`, the tool registrations in `server.py`, anything that mutates a `.kicad_*` file, and text an LLM reads at runtime (tool descriptions, `.claude/skills/**`, `CLAUDE.md`, `docs/CONTEXT.md`, `docs/dispatch/**`). core: other `src/boardproof/` code and tests. config/ops: `pyproject.toml`, `evals/`, fixtures. docs: the other `docs/**`, `README.md`. Critical-class text needs a CLEAN adversarial review before it is committed, even from a planning ticket.
- P10: Dispatch freely under 95% of the 5-hour window; stop at 95% weekly (`python docs/playbook/plugin/scripts/usage.py`, or the global CLAUDE.md). A job past about 3x its expected duration is stopped and escalated. `kicad-cli` and router jobs run under `timeout`.
- P11: `python <tree>/scripts/batch_gate.py`, run by the builder at the end of its ticket on a committed, clean tree in the background (`docs/dispatch/builder.md`, Tests) and by the coordinator before a merge. It ends with `BATCH GATE <sha7>: GREEN|RED`. Its rules, figures and timeouts: `docs/TESTING.md` ("The batch gate") and the P11 section of `docs/HISTORY.md` (the gate's printed "fork playbook P11" means that section). Known reds only in `scripts/known-red.txt` (each names its owning ticket; empty now), allowed skips only in `scripts/known-skips.toml`; adding either needs its own ticket and a review. While a gate runs, start no more than 2 other runs.
- P12: Everything is local; there are no PRs and no `land.sh`. A builder pushes its own `ticket-<n>` branch (`git push -u origin ticket-<n>`; the plugin's hand-back gate refuses a branch with no upstream or unpushed commits) and never `main`; the branch is deleted after the merge. The coordinator squash-merges into local `main` (one commit) only after a CLEAN review at the pinned sha (`git rev-parse ticket-<n>` equals the reviewed sha in the ticket) and no failure outside the known-red list; then pushes `main` (P1). Trailers come from the session's attribution block.
- Tools, not scripts: operations on collections, as a checkpointed propose/confirm pair; when no tool exists, build the tool through the write layer on `kicad_tools`' low-level API (hard rule 1; until build ticket 42 lands, the interim rule in `docs/ARCHITECTURE.md` decision 1), never a one-off script or a hand edit.
