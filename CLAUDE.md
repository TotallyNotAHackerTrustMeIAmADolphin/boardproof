# CLAUDE.md

Agent-facing rules for this repo. Read `docs/CONTEXT.md` (glossary), then `docs/ARCHITECTURE.md` (design, decisions, known gotchas), `docs/ROADMAP.md` (acceptance ladder, non-goals) and `docs/TESTING.md` (acceptance gate) before changing code. New to the repo: `README.md` and `docs/OVERVIEW.md` give the picture in ten minutes, and `CONTRIBUTING.md` is the human contributor's page.

## Project, as of the 2026-10-11 pivot

Kicad-MCP is a Python MCP server (`src/kicad_mcp/`, around 4,090 tests as collected on 2026-10-29) that automates KiCad PCB work: sourcing, schematic, placement, routing, verification and manufacturing export. **Rung 1 has boards with `PASS (necked)` from the gate (official batches under protocol 6: Freerouting 5 of 5; a PASS with forced necks, counted and labelled, never a plain PASS). No plain PASS exists yet, and the rung-1 board changed afterwards (protocols 7 and 8) and has no official batch under the current protocol.** One earlier run on openMPPT claimed "routed" and was wrong. The product promise is therefore tiered by board class. The **Copilot tier** is the default. The **Autonomous tier** is earned one board class at a time by passing the acceptance gate on the acceptance ladder.

## Hard rules (no exceptions)

1. **Never hand-edit KiCad files.** `.kicad_sch`, `.kicad_pcb`, `.kicad_sym`, `.kicad_mod`, `.kicad_pro` and `.kicad_dru` are never patched with Read/Write/Edit/sed, not even for a "small fix". KiCad reads tokens, not layout, but a text edit easily breaks what it does depend on: a raw line break inside a string silently drops a whole sub-sheet, a reordered token makes pads lose their nets with no error, an unquoted number or an unknown token fails the load, and pad angles are stored board-absolute. Make every mutation through this project's MCP tools, or, where no tool exists yet, through the project's write layer on `kicad_tools`' low-level S-expression API. Never mutate through the high-level models' setters or `save`. Do not write raw text.
2. **Never trust `kicad_tools` position or geometry convenience properties without cross-checking.** `Pad.position`, `Footprint.position` and `Zone.polygon` have all returned board-absolute coordinates that were wrong by the board/page origin. `pad.size = (...)` is silently not saved. Each of these has already led to a confident false claim, including "mounting holes 30-90 mm off the board" when they were not. Before you state, act on or report any position or geometry fact, read the raw `(at ...)`, `(size ...)` or `(polygon ...)` S-expression, or cross-check against it. Never base a mutation on a convenience property alone.
3. **Never call a board routed or done without a `verify_board` PASS.** The PASS must come from the acceptance gate (docs/TESTING.md): one machine-checked verdict with zero unconnected items on every net, zero error-level DRC, and all zones filled and verified. All figures come from `kicad-cli` output. Samples, category counts, "0 shorts", a router's self-reported score and `kicad_tools` properties are never evidence of done. `verify_board` exists (`src/kicad_mcp/verify_board.py`, always loaded). Only its `PASS` counts; `FAIL` and `INCOMPLETE` never do. Without a PASS, make no routed or done claim at all. Report the complete per-net unconnected list and the complete violation list from `verify_board` (or from `kicad-cli pcb drc` when the gate cannot run) instead.
4. **openMPPT is frozen** until ladder rungs 1 and 2 pass. Do not route, place or "fix" it. The board lives in a separate repository (the MPPT hardware project, which is not part of this repo), branch `hardware/PCB_v1.3`.

## Working convention

- **For outside readers:** planning lives in the GitHub issues of this repository, which may be public; there is no private planning folder. Public docs state a fact in words and cite a ticket as a plain reference (for example "build ticket 112"); an issue migrated from the old planning records starts with "formerly build ticket N". The glossary in `docs/CONTEXT.md` explains ticket, map and protocol. The old backlog ids resolve through the maintainers' archive and may not be resolvable from a public copy.
- **Planning and tickets are GitHub issues** (`docs/WORKFLOW.md`). A map is one issue labelled `map` with a task list of its tickets; a ticket is an issue labelled by type (`build`, `research`, `decision`, `task`) plus `critical`, `parked` or `needs-owner` where they apply, with `Blocked by #n` lines; its status is open or closed, and its Answer and review verdicts are comments. Read and write them with `python scripts/issues.py` (`show`, `create`, `comment`, `close`, `list`), which refuses any text that `scripts/check_publishable.py` flags. Write every issue and comment so that it may become public: facts only, no real name, no machine path, no candid judgement of a person or another project. Chart a map (a planning method; the Wayfinder skill is one way) for any effort too big for one session, and do not presuppose the answer. The ticket IDs that code and older tickets cite (P1-xx to P5-xx, M-0x) resolve through the maintainers' archive.
- **Work a map's frontier in parallel.** Dispatch each unblocked, unclaimed ticket as its own subagent. Each build ticket runs on its own local branch in its own hand-made worktree (`git worktree add -b ticket-<n> <scratch>/work/wt-<n> main`), branched from the current local `main`. Do not use `isolation: "worktree"`: it bases on `origin/main`, not on the local `main`. Planning and research tickets need no worktree: they live in issues and their comments. Brief each agent with the acceptance criteria, the contracts it must follow (`ToolsetBuilder`, `SourcingProvider`, the checkpoint helper with its self-check and drift guard) and its file ownership. Give genuine encouragement in dispatches, not only specs.
- **Every build ticket gets an adversarial review.** The playbook fork (`docs/playbook/PROJECT-KICAD-MCP-PLAYBOOK.md`) holds the review rules: what a finding blocks, the delta loop and the stop rule. In short, every finding is classed BLOCKS or FOLLOW-UP, and CLEAN means no BLOCKS finding. A BLOCKS finding becomes a failing test before its fix. FOLLOW-UPs go into build tickets at the merge. Re-review the delta until the verdict is CLEAN; stop after the third delta review and escalate. The stop rule never permits a merge without CLEAN. Then, when the change touches behaviour, tool text an LLM reads, pins or protocols (otherwise targeted tests; see the commit bullet below), run the full suite from the worktree root with the shared interpreter by absolute path (`<main checkout>/.venv/Scripts/python.exe`) and `PYTHONPATH=<worktree>/src`; the run counts only if `kicad_mcp.__file__` lies inside the worktree and pytest's `rootdir:` line names the worktree, because the shared `.venv`'s editable install points at the main checkout. The coordinator squash-merges the branch into local `main` only when the review is CLEAN, `git rev-parse ticket-<n>` equals the reviewed sha recorded in the ticket, and no test fails outside the known-red list. The verdict, the reviewed commit and the review text go into the ticket as comments on its issue. A change to critical-class text (`CLAUDE.md`, `docs/CONTEXT.md`, `.claude/skills/**`, tool descriptions) needs a CLEAN adversarial review before it is committed, even from a planning ticket.
- **Record findings immediately** in docs/ARCHITECTURE.md's known facts, the ticket's Answer (an issue comment) and one line in the map issue's Decisions-so-far.
- **Commit after every closed ticket and push right away**, without asking (durable owner authorisation, 2026-10-19). This holds for every commit on `main` and every research branch. Never force-push, never delete `main`. Run the full suite first when the change touches behaviour, tool text an LLM reads, pins or protocols, and once at each milestone such as the export (owner rule of 2026-10-29, docs/TESTING.md, "Test suite"); never run it twice for one logical change. A change that only moves files or edits docs, comments or docstrings gets review plus targeted tests instead, but edits to critical-class text (`CLAUDE.md`, `docs/CONTEXT.md`, `.claude/skills/**`, tool descriptions) are not "docs" for this purpose and need the full suite (`KICAD_DEMOS_REQUIRED=1 KICAD_ROUTING_TOOLS_REQUIRED=1 .venv/Scripts/python.exe -m pytest -m "not network" -q`). Known reds are only the list in the playbook fork's P11 (later build ticket 45's known-red file); adding one needs its own ticket and a review, and any other failure blocks the commit or merge. Name the known reds that failed in the commit. There is no hosted CI (owner decision 2026-10-19: no paid GitHub), so this local run is the test gate.
- **A rule that was broken once becomes a test or a hook.**
- **Batch tools, not one-item-per-call.** Tools operate on collections and patterns ("place all decoupling caps", "fix every violation of type X"), not on one item per call. This is a project requirement.
- **Ask the user only when truly blocked**: credentials, accounts, or a scope or direction call. Otherwise make the call, write the reasoning into the ticket, and keep moving.
- **Don't over-wait.** If a long-running job passes about 3x its expected duration, stop it and escalate (for the batch gate, the stop point is the worst case it prints at its start; its own timeouts bound every step: docs/TESTING.md, fork playbook P11). Do not wait silently for hours.
- Use the `mcp-builder` skill when defining tool schemas.
